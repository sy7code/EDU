# 성장 페이스 — 프로젝트 기록

2026 INHA AX-EDU 해커톤. 팀명 "성장 페이스". 작성자 역할: 프론트엔드.

## 1. 개요

- **문제**: 정규 수업 밖 자기주도학습은 학생이 어떤 질문을 하고 어떻게 이해를 넓혔는지 기록으로 남지 않는다. 학생은 자기 과정을 돌아보기 어렵고, 교사는 결과·점수만으로 도움이 필요한 지점을 알기 어렵다.
- **목표**: 학습 시작·종료를 토스 페이스패스(또는 QR·바코드·교사 확인)로 인증하고, 그 사이의 메모·질문·AI 논의·성찰을 남기며, 교사가 근거 기반으로 피드백·관찰 평가하는 플랫폼.
- **제약**: 지원 기술(슈퍼스쿨, 토스 페이스패스) 상세는 2일차 공개 → 1일차는 mock으로 전체 흐름을 먼저 완성. 사용자는 미성년자이고 생체 인증이 관련되어 개인정보·보안이 핵심 평가 요소(윤리성 10점).

## 3. 기술 선택

`docs/decisions.md`는 아직 없음(해커톤 일정상 생략). 주요 결정만 기록한다.

- **API 계약(타입) 먼저 + mock 우선 개발**: `src/types/domain.ts`·`src/api/types.ts`를 백엔드와 공유하고 화면은 `Api` 인터페이스에만 의존. 대안(백엔드 완성 대기)보다 병렬 개발 가능. 결과: 2일차 연동은 함수 단위 교체로 범위가 좁아짐. 단점: mock 규칙과 실제 서버 규칙이 어긋날 위험 → `mockApi.test.ts`를 백엔드 검증 시나리오로 명세에 지정.
- **mock에 백엔드 규칙을 실제로 구현**: 권한·인증 이벤트 1회 사용·동의·마스킹을 mock이 강제하고 테스트로 고정. 화면 개발용 가짜가 아니라 "명세의 실행 가능한 버전"으로 씀. 단, 브라우저 코드라 보안 경계는 아님(문서에 명시).
- **얼굴 정보를 받지 않는 구조**: 토스가 생체정보를 보관하고 우리는 인증 결과만 받음 → 민감정보 직접 처리 회피.
- **기록 단위 공개 범위(TEACHER/PRIVATE) + 동의 철회 즉시 숨김**: 학생이 공유 범위를 결정. 슈퍼스쿨 슈퍼보드의 "공개 범위" 개념과도 맞음.
- **AI는 제안만, 교사가 확정**: 채점 근거 ID 필수, 근거 없으면 판단 보류. 학생은 확정본만 봄.
- **UI 라이브러리**: shadcn/ui 대신 Tailwind로 소형 컴포넌트 직접 작성 (CLI 셋업 시간 절약).

## 4. 어려움과 극복

- **지원 기술 형태 오판**: 페이스패스를 웹훅 방식으로 가정했으나 실제 문서는 단말기 SDK. → `FaceAuthProvider` 어댑터 뒤에 숨겨 두어 인터페이스만 바꿈. 배운 점: 미공개 외부 연동은 어댑터 경계를 먼저 둔다.
- **입력창 내용 소실**: 저장 요청 중 다음 내용을 입력하면 `onSuccess`의 초기화가 새 입력을 지움(브라우저 확인 중 발견). → 제출 시 값을 고정하고 즉시 비우며 실패 시 복원. 같은 패턴 3곳 동시 수정.
- **AI 대화 원문 저장**: AI 전송은 마스킹했지만 저장은 원문이라 교사 화면에 전화번호 노출. → 실패 테스트로 재현 후 마스킹본 저장.
- **보안 리뷰 지적 6건**(독립 리뷰가 찾고 직접 재현): 마스킹 우회(`가온이`, `010.1234.5678`, 하이픈 없는 주민번호가 `05[연락처]`), 중복 인증으로 종료 시각이 시작보다 앞섬(재현: 시작 10:00:10, 종료 10:00:00, 0분), 학생의 반 명단 조회(30명), 미동의 학생 성찰 노출, 예측 가능한 QR 토큰, 동의 철회·이력·만 14세 미만 미강제. → 재현 테스트 13개 RED 확인 후 수정. 배운 점: "규칙을 화면에서만 검사"한 곳이 대부분이었음 → 규칙은 데이터 계층에서 테스트로 고정.

프론트 완료 기준(`docs/plans/2026-11-13-frontend-plan.md`) 대비:

## 6. 한계와 발전 가능성

- 권한 검사는 mock(브라우저) 안에 있음 → 실제 보안은 백엔드 RLS·서버 함수 구현과 같은 시나리오 검증이 필요.
- 페이스패스 결과를 단말기가 보내므로 위조 가능성. 토스의 서버 간 검증 API 존재 여부 미확인. 키오스크 기기 토큰 발급 방식 미설계.
- LOW 미수정: 종이 기록 더블클릭 중복, 키오스크 SDK 타임아웃, 환경변수 없을 때 mock 기본값, 진행 중 세션 채점 확정·서버 입력 검증.
- AI는 규칙 기반 mock 응답 → 실제 LLM 연결 시 근거 ID 검증·프롬프트 인젝션 대응을 서버에서 구현해야 함.
- 마스킹은 일반 단어와 같은 이름을 과하게 가림.
- 다음: Supabase 연동, 리포트(현장 양식) 화면, 모바일 폭·키보드 접근성 점검, 배포.

## 7. 회고

- **잘한 것**: 외부 연동을 어댑터로 분리해 실제 문서가 달라도 화면을 고치지 않음. 브라우저로 직접 흐름을 돌려 단위 테스트가 못 잡은 버그 3건을 찾음. 독립 리뷰로 내가 놓친 규칙 위반을 찾고 재현 후 고침.
- **아쉬운 것**: 첫 구현의 TDD가 느슨했음(stub 예외로 본 RED, 일부 테스트는 구현 후 작성). 규칙을 처음부터 데이터 계층 테스트로 고정했다면 보안 지적 다수를 미리 막았을 것.
- **다음에 시도할 것**: 권한·동의 규칙을 결정표로 먼저 만들고 테스트를 표에서 생성. 커밋을 기능 단위로 더 일찍 나누기.

## 2026-11-14 추가: 단원 테스트 + 교사 종합 보드

### 개요
교사가 학습 시간·기록·단원 테스트 결과를 한 화면에서 종합해 학생 수준과 학습 방식을 파악하도록 한다. 설계 `docs/01-mvp.md`, 계획 `docs/plans/2026-11-14-unit-quiz-plan.md`, 브랜치 `feat/unit-quiz`.

### 진행·결정
- 문제 출처 3안 비교 → **A안: AI 초안(성취기준 근거) → 교사 승인**만 출제 (사용자 선택). 교사 문제은행(B)은 부담, AI 즉석 출제(C)는 "상상해서 쓰지 않음" 원칙 위배로 제외.
- 실행: 이 세션에서 직접(inline) TDD, 작업 6개 + 최종 리뷰(Opus 서브에이전트).
- 함께 고침: "수기 확인" 버튼 → "선생님이 확인"(결과 알림이 스크롤 밖에 떠 아무 반응 없는 것처럼 보이던 문제).

### 어려움과 극복
- **startSession이 unitId를 버림**(단원 테스트가 전부 QUIZ_NOT_AVAILABLE) → 고치면서 "자기 반·같은 과목 단원만" 검증을 추가(테스트 2개 RED→GREEN).
- **제출 직후 결과 화면을 건너뜀**(브라우저 확인 중 발견): 제출 성공 시 응시 캐시를 채우자 상위 화면이 "이미 응시"로 판단 → 캐시 갱신을 결과 확인 후로 미룸.
- **꺼진 쿼리에서 `data!` 렌더 오류**(콘솔): 조건부 쿼리 3곳 `!data` 가드. 수정 전 재현은 못 함.
- **최종 리뷰 Important**: ① 제출 채점이 출제 시점과 다른 문제 집합으로 될 수 있음 → 출제 스냅샷 채점 ② 이미 제출 상태에서 화면 막힘 → 결과/돌아보기 이동. 재등급: 정답 위치 편향(시드 정답 대부분 1번) → 선택지 섞기, 신호가 다른 세션 값을 섞음 → 같은 세션 짝. 섞기 테스트 첫 버전이 구현 전에도 통과해 순서 비교로 강화.

### 결과
- 완료 기준(계획 Task별): Task 1~6 원장 기록 완료. 브라우저로 학생(단원 선택→테스트→결과·해설→돌아보기→내 기록, 빈 단원)·교사(AI 초안→수정→승인, 종합 보드 신호, 대시보드 최근 테스트) 확인.
- 테스트 71 → **74개 통과**, 타입 검사 통과, 빌드 성공(JS 약 465KB / gzip 약 145KB).
- 보안: gitleaks(이력·작업트리) 유출 없음, `npm audit` 0, 빌드 비밀키 문자열 0, `dangerouslySetInnerHTML`·`console`·`eval` 없음. 정답은 제출 전 학생 API로 내려가지 않음(테스트), 동의 철회 시 교사에게 결과 비공개(테스트).

### 한계 (미룬 것)

### 회고
